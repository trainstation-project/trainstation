# Qwen3-30B-A3B preparation for 8 B300 GPUs

This recipe prepares continued pretraining from the original BF16
`Qwen/Qwen3-30B-A3B` checkpoint, using MXFP8 attention projections and expert
grouped GEMMs. Expert weight gradients use BF16 through TorchAO's
`mxfp8_rceil_wgrad_with_hp` recipe. Router gates and the output head remain
outside MXFP8.
Preparation does not start a trainer or execute a model forward/backward pass.

| Setting | Value |
| --- | --- |
| Dense FSDP2 / expert parallelism | 8 / 8, on the same eight GPUs |
| Expert FSDP / TP / PP / CP / DP replication | 1 / 1 / 1 / 1 / 1 |
| Experts per GPU per layer | 16 |
| Maximum context / microbatch tokens per rank | 8192 / 8192 |
| Global tokens per optimizer step | 65536, without gradient accumulation |
| Expert dispatcher | HybridEP, non-blocking capacity factor 1.0 |
| Expert token padding | 128 |
| Expert GEMM recipe | MXFP8 forward/input gradients, BF16 weight gradients |
| CUDA graphs | Enabled for forward/backward |
| Compilation / activation checkpointing | Model compilation / full checkpointing |
| FSDP reshard after forward | Never |
| Persistent training dtype / FSDP compute / reduction | FP32 / BF16 / FP32 |
| Sample job | 100 steps, AdamW LR 1e-5, 10 warmup steps |

The sample learning rate and duration are preparation defaults, not a tuned
convergence recipe. The first run loads HF weights directly; an existing
checkpoint in the output directory takes precedence on restart. The final
checkpoint is model-only BF16. Full optimizer-resume checkpointing should be
configured separately for a longer training job.

## Environment

From the repository root, with `uv`, Python 3.12, a C++ compiler, and the NVIDIA
driver available:

```bash
bash scripts/setup_qwen3_b300.sh
source outputs/qwen3_30b_mxfp8_prep/venv/bin/activate
export CUDA_HOME="$VIRTUAL_ENV/lib/python3.12/site-packages/nvidia/cu13"
export PATH="$CUDA_HOME/bin:$PATH"
export LD_LIBRARY_PATH="$CUDA_HOME/lib:${LD_LIBRARY_PATH:-}"
```

The setup script pins PyTorch `2.15.0.dev20260921+cu130`, TorchAO
`0.19.0.dev20260922+cu130`, CuTeDSL `4.5.2`, CUDA compiler/NVVM/CRT `13.0.88`,
and CCCL `13.0.85`. NVCC, NVVM and compiler runtime headers must match:
mixing their 13.4 and 13.0 releases fails compilation.
The checkpointing package is pinned to source revision
`1391408e294286acfa30358ba0c665ba1cad2c76`, providing the APIs used by this
checkout's optional checkpoint backend and its type checks.

HybridEP is built for SM103a from the repository's CI-pinned DeepEP revision
`f725d29699f5bda9ba789456bb9579af69844685`, on the `hybrid-ep` branch. This
provides `deep_ep.HybridEPBuffer`; a DeepEP V2 installation is not a substitute
for that API. The build is single-node and does not require the multinode
DOCA backend. Compiler libraries and source/build outputs stay under the
ignored `outputs/qwen3_30b_mxfp8_prep` directory.

## Model and sample data

```bash
python scripts/prepare_qwen3_30b_b300.py
```

The downloader uses pinned revisions and writes:

- `assets/hf/Qwen3-30B-A3B/`: tokenizer, model configuration, index and 16 BF16
  safetensors shards, approximately 61 GB in total.
- `data/qwen3_30b_c4_sample/train.jsonl`: the first 16,384 documents from the
  first English C4 training shard; 7,673,320 content tokens with this tokenizer.
- `data/qwen3_30b_c4_sample/validation.jsonl`: the first 512 documents from
  the first English C4 validation shard; 243,613 content tokens.
- `data/qwen3_30b_c4_sample/manifest.json`: source revisions, counts and SHA256
  checksums. Content counts exclude added EOS tokens.

Model revision: `ad44e777bcd18fa416d9da3bd8f70d33ebb85d39`.
C4 revision: `1588ec454efa1a09f29cd18ddd04fe05fc8653a2`, license `odc-by`.
The JSONL preserves source URLs and timestamps. These bounded shard prefixes
are preparation samples, not a representative convergence corpus. The recipe
uses only the training split; the validation sample is available separately.

The data loader packs documents into fixed 8192-token batches and repeats the
sample when necessary. The tokenizer has 151,669 entries within the model's
151,936 embedding rows; unused embedding rows are expected.

## Checks that do not train

```bash
python -m pytest tests/unit_tests/cpu/test_qwen3_b300_recipe.py -q
python -m torchtitan.config.manager \
    --module torchtitan_recipes.qwen3 \
    --config qwen3_30b_a3b_mxfp8_fsdp8_ep8_b300
```

The recipe test checks that CUDA graphs require non-blocking HybridEP, router
gates are excluded from MXFP8, dispatch padding and capacities match the token
budget, and initial checkpoint loading is enabled. The configuration command
only parses the recipe; it does not initialize the trainer.

The optional GPU regression test
`tests/unit_tests/gpu/test_qwen3_b300_recipe.py` checks finite gradients and
exactly zero weight gradients for experts receiving zero tokens, with and
without extra dispatch capacity. This matters for the pinned PyTorch/TorchAO
versions: the all-MXFP8 `mxfp8_rceil` grouped weight-gradient path returned
uninitialized values for empty experts in a standalone reproduction and caused
the full model's first step to fail the gradient-finiteness check. TorchAO's
BF16 weight-gradient recipe returns zeros for these experts while retaining
MXFP8 forward and input-gradient GEMMs.

Capacity factor 1.0 uses worst-case dispatch sizing. Lower factors can silently
drop routed tokens on overflow. If memory is tight, reduce the per-rank token
budget and update the dispatch capacity together before shrinking this factor.
The benchmark below exercises CUDA graph capture/replay and reports memory and
throughput. It is a short numerical smoke test, not a convergence study.

## Launch later

The following command starts training. It is provided for the later run and
must not be used as a preparation check:

```bash
NGPU=8 MODULE=torchtitan_recipes.qwen3 \
CONFIG=qwen3_30b_a3b_mxfp8_fsdp8_ep8_b300 ./run_train.sh
```

Outputs go to `outputs/qwen3_30b_mxfp8_b300/`. Weights, sample data, virtual
environment, dependency sources, build products and logs are ignored by Git.

## Measured 100-step benchmark (2026-09-22)

The corrected recipe completed 100 steps on eight NVIDIA B300 SXM6 AC GPUs,
processing 6,553,600 tokens from the prepared C4 sample. CUDA graph capture
completed at step 3 and subsequent steps used replay. All 100 losses and
gradient norms were finite. The final model-only BF16 checkpoint was saved.

| Metric | Steps 11-100 |
| --- | ---: |
| Measured steps / training time | 90 / 94.0896 s |
| Mean / median step time | 1.04544 / 1.03306 s |
| Global throughput | 62,687 tokens/s |
| 24-hour throughput projection | 5.416B tokens/day |
| Model TFLOPS per GPU | 294.46 |
| MFU relative to dense FP8 peak | 6.54% |
| MFU relative to BF16 peak | 13.09% |
| Rank-0 peak PyTorch reserved / active memory | 83.41 / 80.05 GiB |
| Rank-0 allocation retries / OOMs | 0 / 0 |

Throughput is total tokens divided by total measured time, not an arithmetic
average of per-step rates. These timings include data loading, forward/backward,
communication, and optimizer updates. They exclude startup, compilation, the
first 10 steps, and checkpoint writes. The final checkpoint took 25.62 seconds;
frequent checkpointing reduces wall-clock tokens/day. At the measured training
rate, 1B tokens takes about 4.43 hours before checkpoint and other downtime.

MFU uses TorchTitan's model-work convention: 3,041,867,776 matmul-active
parameters (excluding the input embedding), with the attention term for the
8192-token context:

```text
FLOPs/token = 6 * 3,041,867,776 + 12 * 48 * 32 * 128 * 8192
            = 37,578,559,488
MFU = global_tokens_per_second * FLOPs_per_token / (8 * peak_FLOPs_per_GPU)
```

This excludes activation-checkpoint recomputation and does not halve the
quadratic attention term for causal sparsity. The dense FP8 reference is
4.5 PFLOPS/GPU, half the sparse FP8 figure in
[NVIDIA's eight-GPU DGX B300 specifications](https://www.nvidia.com/en-us/data-center/dgx-b300/).
The BF16 reference is 2.25 PFLOPS/GPU. This is mixed MXFP8/BF16 training, so both
denominators are reported explicitly; they are normalization conventions, not
measurements of individual kernels' utilization. TorchTitan intentionally
prints `mfu: N/A` for quantized models, so the values above were calculated
from the measured throughput and model FLOPs.

Reproduce after activating the environment above, using a fresh output folder
to avoid resuming the completed checkpoint:

```bash
export CPLUS_INCLUDE_PATH="$CUDA_HOME/include/cccl:${CPLUS_INCLUDE_PATH:-}"
export NVCC_APPEND_FLAGS="-I$CUDA_HOME/include/cccl"
export TOKENIZERS_PARALLELISM=false
benchmark_dir=$(mktemp -d outputs/qwen3_b300_benchmark.XXXXXX)
NGPU=8 MODULE=torchtitan_recipes.qwen3 \
CONFIG=qwen3_30b_a3b_mxfp8_fsdp8_ep8_b300 ./run_train.sh \
    --dump-folder "$benchmark_dir" \
    --training.steps 100 --metrics.log-freq 1 --metrics.enable-tensorboard
```

Local evidence is under `outputs/qwen3_30b_mxfp8_benchmark/`: `train.log`,
`summary.json`, TensorBoard events in `run/tb/`, and the checkpoint in
`run/checkpoint/`. The first failed all-MXFP8 attempt and isolated kernel
diagnostics are also retained there. No generated evidence or checkpoints are
tracked in Git.
